app deploys the selected Artemis variant onto the chair's remote VM over

## Findings and known operational issues on the remote target

1. **HSTS blocks browser access to `*.artemis.cit.tum.de` with a self-signed
   certificate.** `ma-ning.artemis.cit.tum.de` is a subdomain of
   `artemis.cit.tum.de`, whose production site sends an HSTS header with
   `includeSubDomains`. Any browser that has visited production Artemis pins
   the whole subtree to strict transport security, so Chrome refuses the
   self-signed certificate outright and offers **no "proceed anyway" option**
   (error: "the website sent back unusual and incorrect credentials … this
   site uses HSTS"). The deployment itself was healthy; this is purely a
   client trust problem. Resolutions:
   - immediate: type `thisisunsafe` on the blocked Chrome page (works on HSTS
     pages; no visible input needed);
   - proper: export the VM certificate and trust it in the macOS keychain
     (`security add-trusted-cert -r trustRoot …`), then fully quit and reopen
     Chrome — a system-trusted certificate is not an HSTS violation. Requires
     the certificate's SAN to include the access name;
   - `curl -k` is unaffected by HSTS and remains usable for `/management/info`;
   - long-term (and the reason TUM test servers do not hit this): request a
     real RBG-signed certificate for the name, as the test servers use.
   Access was confirmed after applying a workaround.

2. **eduVPN is a control-node runtime dependency for the entire run.** The
   tunnel must stay connected for the full playbook, not just at connect
   time. This is the concrete answer to the stage-③ runner-placement
   question: a GitHub-hosted runner cannot reach the VM; workflow-izing this
   deployment needs a self-hosted runner inside the MWN/VPN, or an equivalent
   in-network execution path. (DNS resolves publicly, so only the connection,
   not name resolution, depends on the VPN.)

3. **Self-signed certificate lifecycle.** Generated on the VM at
   `/opt/artemis-certs/{fullchain,privkey}.pem` (CN + SAN = access name).
   Replace by overwriting the two files and `sudo docker restart
   artemis-nginx`. Only delete the files while the stack is stopped: the
   files are bind-mounted into the always-restarting nginx container, and a
   restart with the source path missing makes Docker create an empty
   *directory* there, sending nginx into a crash loop. Path is a config-time
   value baked into the generated compose (changing the path ⇒ regenerate the
   package); content can be swapped freely.

4. **Database switch leaves an orphan container and a stale volume.** MySQL
   and PostgreSQL use different containers and different data volumes, so
   switching does not require wiping the old volume to succeed. But the old
   `artemis-mysql` container is not in the new (postgres) compose file and
   survives as an orphan with `restart: always` — remove it
   (`sudo docker rm -f artemis-mysql`) to reclaim RAM on the 8 GB host. Wipe
   the old data volume only for a clean variant experiment, to reclaim disk,
   or to avoid the rotated-password-on-existing-volume access-denied loop
   documented in `composer-closing-validation-2026-08-22.md` (a database
   applies credentials only on first initialization). A freshly switched
   database boots empty; the admin account is recreated from env credentials.

## Conclusion

A selection exported from the feature-model app as a remote-ansible package
deploys the matching Artemis variant onto the chair's real remote VM over
eduVPN, with no hand-editing beyond the documented admin inputs (host
connection line, environment values, secret material). Both variants — a
minimal MySQL baseline and a PostgreSQL variant carrying six bound
integrations — render the expected profile line, keep the NULL-OVERRIDE in
the real render, and boot to a healthy stack. The remaining
open items are client-side certificate trust (HSTS) and workflow-stage
network placement, both of which are environment concerns rather than
composer defects.
